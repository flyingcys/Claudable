# Claudable 手工启动说明

## 1. 当前仓库结构概览

这个仓库是一个以 Web 为主、桌面端为辅的 AI 应用构建器，当前主链路如下：

- 前端与接口层：`Next.js 15` + `React 19`，使用 `app/` 路由。
- 本地数据层：`Prisma + SQLite`，数据库文件默认在 `data/cc.db`。
- 启动入口：Web 开发服务由 `scripts/run-web.js` 拉起，桌面端由 `scripts/run-desktop.js` 拉起。
- 环境初始化：`scripts/setup-env.js` 会自动创建 `.env`、`.env.local`、`data/`、`data/projects/`、`prisma/data/`。
- AI CLI 适配：仓库内置了 `claude`、`codex`、`cursor-agent`、`qwen`、`glm` 的状态检查与接入逻辑。
- 如果需要修改页面里 `Codex CLI` 的模型下拉列表，参考 [codex-cli-模型列表写死位置.md](./codex-cli-模型列表写死位置.md)。

## 2. 手工启动前提

### 2.1 基础环境

- Node.js `>= 20`
- npm `>= 10`
- Git

当前仓库已验证环境：

- Node.js: `v22.21.1`
- npm: `11.12.1`

### 2.2 AI 功能前提

如果你只是要把 Web 服务跑起来，下面的 CLI 不需要全部提前装好。

如果你要在界面里真正发起 AI 代码生成，还需要至少准备一种可用 CLI，并先完成登录：

- `claude`
- `codex`
- `cursor-agent`
- `qwen`
- `glm`（当前实现沿用 Claude CLI 的安装/登录状态）

## 3. 手工启动步骤

### 3.1 安装依赖

在仓库根目录执行：

```bash
rtk npm install
```

这一步会自动触发 `postinstall -> npm run ensure:env`，完成以下初始化动作：

- 生成 `.env`
- 生成 `.env.local`
- 创建 `data/cc.db`
- 创建 `data/projects/`
- 自动选择 Web 端口

### 3.2 启动 Web 开发服务

```bash
rtk npm run dev
```

等价入口：

```bash
rtk npm run dev:web
```

启动脚本会继续自动做两件事：

- 调用 `scripts/setup-env.js`，同步端口与 `NEXT_PUBLIC_APP_URL`
- 检查 SQLite 中是否已有 `projects` 表；如果没有，会自动执行 `prisma db push`

### 3.3 访问服务

默认访问地址：

```text
http://localhost:3000
```

如果 `3000` 被占用，脚本会在 `3000-3099` 范围内自动寻找下一个可用端口，并把结果写回：

- `.env`
- `.env.local`

预览子项目端口池默认范围：

```text
3100-3999
```

## 5. 首次启动现象

首次启动后，端口可能已经监听，但第一次打开页面会明显变慢。这不是端口问题，而是 Next.js 正在做首轮编译。

本次验证里，首页和 `/api/projects` 首次响应都大约在 8 秒后返回 `200`。如果你看到浏览器短时间转圈，先不要急着判断为启动失败。

## 7. 常见排查

### 7.1 页面一直打不开

先看是否真的已经监听端口：

```bash
rtk proxy ss -ltnp | rg ':3000 '
```

再直接探测接口：

```bash
rtk proxy curl -I http://127.0.0.1:3000
rtk proxy curl http://127.0.0.1:3000/api/projects
```

如果端口已监听但首页很慢，优先怀疑首编译，而不是服务没起来。

### 7.2 AI 按钮能看到，但无法真正工作

这通常不是 Web 启动失败，而是对应 CLI 未安装或未登录。先在设置页看状态，或直接在终端确认，例如：

```bash
rtk proxy claude --version
rtk proxy codex --version
rtk proxy cursor-agent --version
rtk proxy qwen --version
```

然后按各自 CLI 的方式完成登录。

### 7.3 数据库不一致

如果升级仓库后本地 SQLite 和 Prisma Schema 不一致，先尝试：

```bash
rtk npm run prisma:push
```

如果仍然不一致，再考虑：

```bash
rtk npm run prisma:reset
```

注意：`prisma:reset` 会清空本地数据。

### 7.4 页面显示“localhost 拒绝了我们的连接请求”

这类问题现在优先按 preview 链路排，不要先怀疑主站 `3000` 没起来。

先查当前项目的 preview 状态：

```bash
rtk proxy curl -s http://127.0.0.1:3000/api/projects/<projectId>/preview/status
```

如果返回里 `url` 为 `null` 或 `status` 不是 `running`，再主动拉起 preview：

```bash
rtk proxy curl -s -X POST http://127.0.0.1:3000/api/projects/<projectId>/preview/start
```

这条接口会直接返回：

- `url`
- `port`
- `status`
- `logs`

也就是当前最有价值的 preview 运行日志。

### 7.5 最后一轮修复后的排障原则

当前仓库里，这次最后一天的修复原理有三条，排障时按这三条理解现象更准确：

1. Codex 在收到 `turn.completed` 时就会立即把 request 收敛到 `completed`，不再依赖 EOF 才落库。
2. Preview 只有真正 ready 后，后端才会把 `previewUrl` 返回给前端；未 ready 会直接失败并回滚状态。
3. 前端在页面初始化和 iframe 报错时，会主动回查 `/preview/status`，必要时自动重新拉起 preview，而不是长期盯着旧的 `localhost` URL。

所以如果你后面再看到类似问题，建议按这个顺序查：

1. `user_requests` 是否真的还在 `running`
2. `/preview/status` 返回的 `url` 是不是当前有效地址
3. `/preview/start` 返回体里的 `logs` 是否显示 preview 已 ready
