# 当前项目 Electron 跨平台打包说明

## 1. 适用范围

本文档说明当前 `Claudable` 仓库如何打包桌面端安装包，覆盖：

- Windows
- Ubuntu / Linux
- macOS

当前仓库的桌面端方案是：

- `Next.js standalone` 产物
- `Electron` 作为桌面壳
- `electron-builder` 负责各平台打包

对应配置可见：

- [package.json](../package.json)
- [next.config.js](../next.config.js)
- [electron/main.js](../electron/main.js)

## 2. 当前仓库的打包配置

当前脚本如下：

```bash
npm run build:desktop
npm run package:win
npm run package:linux
npm run package:mac
```

当前平台目标如下：

- Windows: `nsis`，`x64`
- Linux: `AppImage`
- macOS: `dmg`、`zip`

产物输出目录配置为：

```text
dist/
```

## 3. 打包前提

### 3.1 通用前提

- Node.js `>= 20`
- npm `>= 10`
- 能成功执行 `npm install`
- 仓库根目录可正常执行 `npm run build`

建议先执行：

```bash
rtk npm install
rtk npm run type-check
rtk npm run build
```

虽然 `package:win`、`package:linux`、`package:mac` 都会先跑一次 `npm run build`，但先单独跑一遍更容易提前发现问题。

### 3.2 平台前提

建议在哪个平台发哪个包，就在哪个平台本机打包：

- Windows 包：优先在 Windows 上打
- macOS 包：优先在 macOS 上打
- Linux 包：优先在 Ubuntu / Linux 上打

不建议把这三个目标都压到单一平台跨平台构建。原因很实际：

- Windows 安装器、macOS 签名、公钥链、Linux 桌面依赖都各自有平台差异
- 当前仓库没有额外的跨平台打包适配脚本
- 当前轮次没有做三平台交叉打包实测

## 4. 通用打包步骤

在仓库根目录执行：

```bash
cd /home/share/samba/ai-coding/Claudable
rtk npm install
rtk npm run type-check
rtk npm run build
```

确认 `Next.js` 构建成功后，再执行对应平台的打包命令。

## 5. Windows 打包

### 5.1 命令

```bash
rtk npm run package:win
```

### 5.2 典型产物

当前配置目标是 `nsis` 安装器，所以典型产物会在 `dist/` 下生成：

- `*.exe`

注意：

- 这里的 `exe` 是安装器，不是单文件 portable 可执行文件
- 当前配置只声明了 `x64`

### 5.3 建议

- 优先在 Windows 机器上直接打包
- 如果后续要分发给其他人，建议再补代码签名流程

## 6. Ubuntu / Linux 打包

### 6.1 命令

```bash
rtk npm run package:linux
```

### 6.2 典型产物

当前配置目标是 `AppImage`，所以典型产物会在 `dist/` 下生成：

- `*.AppImage`

### 6.3 建议

- 优先在 Ubuntu 本机打包
- 如果目标环境打开 `AppImage` 失败，先检查系统是否具备对应运行依赖，例如 `libfuse2`

## 7. macOS 打包

### 7.1 命令

```bash
rtk npm run package:mac
```

### 7.2 典型产物

当前配置会在 `dist/` 下生成：

- `*.dmg`
- `*.zip`

### 7.3 建议

- 必须优先在 macOS 本机打包
- 如果要给其他人正式分发，通常还需要 Apple Developer 签名和 notarization
- 当前仓库未看到额外签名配置，所以默认更适合本机测试包，而不是直接公开分发包

## 8. 当前仓库的已知限制

这部分很重要。当前仓库虽然已经具备基础打包配置，但还不能把“有打包脚本”直接等同于“桌面包一定稳定可运行”。

### 8.1 Electron 依赖 Next standalone

当前 [next.config.js](../next.config.js) 开启了：

```js
output: 'standalone'
```

同时 [electron/main.js](../electron/main.js) 会在生产态启动 `.next/standalone/server.js`。

所以打包前必须先保证：

- `npm run build` 成功
- `.next/standalone/server.js` 确实生成

### 8.2 当前轮次未做三平台全链路验收

本轮只核对了仓库配置，没有实际完成以下三项全量验证：

- Windows 打包并安装后首启验证
- Ubuntu 打包并运行 `AppImage` 验证
- macOS 打包后挂载 `dmg` 验证

所以这份文档是“按当前仓库真实配置可执行的打包说明”，不是“三平台全部已验证通过”的验收报告。

### 8.3 运行期仍依赖本地环境

即使桌面包成功生成，应用运行时仍然可能依赖本机环境，例如：

- 本地 CLI 登录态，如 `claude`、`codex`
- 本地数据目录
- SQLite 数据库

也就是说，桌面打包解决的是“桌面应用分发形式”，不是“把所有 AI CLI 一起无感内嵌进去”。

## 9. 常见失败点

### 9.1 `npm run build` 先失败

先单独执行：

```bash
rtk npm run build
```

只要这里不过，后面的 `package:*` 基本也过不了。

### 9.2 缺少 `.next/standalone/server.js`

如果 Electron 生产态提示找不到 standalone server，先确认：

- [next.config.js](../next.config.js) 仍然保留 `output: 'standalone'`
- 本次构建没有中断

### 9.3 打包成功但启动失败

优先排查：

- 桌面包里的 Next standalone 是否完整
- 本地环境变量和数据目录是否可写
- 目标机器是否已经安装并登录需要的 CLI

### 9.4 macOS / Windows 分发时被系统拦截

这通常不是 Electron 代码本身的问题，而是签名和系统信任链问题。当前仓库未补齐正式签名发布链路，因此默认按“开发测试包”理解更准确。

- Windows `exe` 安装器
- Linux `AppImage`
- macOS `dmg/zip`

但更准确的说法是：

- 当前“打包配置已具备”
- 当前“跨平台全链路运行结果未在本轮全部实测”

如果后续要把这条链路做成稳定交付，建议下一步补：

- 至少一次 `Windows / Ubuntu / macOS` 真机打包验证
- 桌面端首次启动验证记录
- 签名与发布说明
