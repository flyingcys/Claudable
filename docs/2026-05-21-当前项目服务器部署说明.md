# 当前 Claudable 平台服务器部署说明

## 1. 结论

当前仓库更适合用 `systemd + Nginx` 部署，而不是完整 Docker 化。

推荐形态：

- `systemd` 负责拉起和守护 Claudable 主 Web 进程
- `Nginx` 负责域名、TLS、反向代理、WebSocket/SSE 转发
- Claudable 主进程继续在宿主机上直接调用本机 CLI，并在本机文件系统里保存 SQLite 和项目数据

不建议把当前平台完整 Docker 化，原因不是“不能跑”，而是“会把当前代码里的几个宿主机假设都变复杂”：

1. Web 进程会直接检查并调用宿主机 CLI，例如 `claude`、`codex`、`cursor-agent`、`qwen`。
2. 项目数据依赖本地文件系统，至少要稳定保留 `data/cc.db`、`data/projects/`、`.env`、`.env.local`。
3. preview 不是静态产物，而是平台运行时按项目再拉起 `npm run dev -- --port 31xx` 的子进程。
4. preview 当前默认生成并回传 `http://localhost:31xx`，这个语义在容器和远程浏览器场景里都会更绕。

如果只是想把主站勉强容器化，理论上可以做；但如果目标是“当前 Claudable 全功能可用”，仍建议先用宿主机部署。

## 2. 当前仓库的部署前提

### 2.1 基础软件

- Linux 服务器，建议自带 `systemd`
- `Nginx`
- `Node.js >= 20`
- `npm >= 10`
- `Git`

### 2.2 运行账号

建议单独准备一个固定账号，例如 `claudable`，并保证下面几件事成立：

- 仓库目录可读写
- `data/`、`public/uploads/` 可写
- 该账号的 `PATH` 能找到你实际安装的 CLI
- 该账号的 `HOME` 固定，不要用临时账号或每次变化的工作目录

### 2.3 网络前提

- 80/443 对外开放给 `Nginx`
- 3000 只监听本机回环，由 `Nginx` 反代
- 3100-3999 保留给 preview 子项目端口池，当前建议只在服务器本机使用，不直接对公网暴露
- 服务器需要能访问 npm registry、GitHub、Vercel、Supabase，以及你实际要用的 AI CLI 上游服务

### 2.4 CLI 前提

如果你只要求主站页面能打开，CLI 不一定要全部装好。

如果你要求平台内 AI 生成能力可用，至少要在同一个运行账号下准备并登录好一种 CLI。当前仓库会直接检查：

- `claude`
- `codex`
- `cursor-agent`
- `qwen`
- `glm` 当前实现沿用 Claude 的安装/登录状态判断

## 3. 目录与持久化建议

最简单的方式是直接在固定目录原地部署，例如：

```text
/srv/claudable/app
```

如果后续你会做版本切换或发布目录轮换，建议把下面这些内容放到持久化目录，再软链回仓库：

- `data/`
- `public/uploads/`
- `.env`
- `.env.local`

其中最不能丢的是：

- `data/cc.db`
  说明：SQLite 主库，项目、消息、会话、preview 元数据都在这里。
- `data/projects/`
  说明：平台生成的项目源码、依赖、assets 都在这里。
- `ENCRYPTION_KEY`
  说明：数据库里的环境变量是加密存的，密钥变了，已有密文就无法正常解密。
- CLI 登录态目录
  说明：必须保留在运行账号自己的 `HOME` 下。具体目录取决于 CLI 本身，不建议把服务跑成无状态临时用户。

## 4. 首次部署步骤

以下示例假设仓库部署在 `/srv/claudable/app`，服务账号叫 `claudable`。

### 4.1 拉代码并安装依赖

```bash
sudo -u claudable git clone <你的仓库地址> /srv/claudable/app
cd /srv/claudable/app
rtk npm ci
```

`npm ci` 结束后，仓库的 `postinstall` 会自动执行 `scripts/setup-env.js`，因此默认会生成：

- `.env`
- `.env.local`
- `data/cc.db`
- `data/projects/`

### 4.2 校正环境变量

第一次生成出来的 `NEXT_PUBLIC_APP_URL` 默认通常还是 `http://localhost:3000`，服务器部署前要改成你的正式域名。

建议至少确认这些键：

```dotenv
DATABASE_URL="file:../data/cc.db"
PROJECTS_DIR="./data/projects"
ENCRYPTION_KEY="请保留首次生成的固定值"
PORT=3000
WEB_PORT=3000
NEXT_PUBLIC_APP_URL="https://claudable.example.com"
PREVIEW_PORT_START=3100
PREVIEW_PORT_END=3999
```

建议把服务器专属覆盖值写在 `.env.local`，并把 `.env` / `.env.local` 一起纳入持久化范围。

### 4.3 初始化 Prisma 并构建

```bash
rtk npm run prisma:generate
rtk npm run prisma:push
rtk npm run build
```

这里不要跳过 `prisma:push`。开发模式下 `scripts/run-web.js` 会自动兜底同步数据库结构，但生产模式的 `npm run start` 不会帮你自动做这一步。

### 4.4 安装并启动 systemd 服务

把下面的 unit 保存为 `/etc/systemd/system/claudable.service`：

```ini
[Unit]
Description=Claudable Web
After=network.target

[Service]
Type=simple
User=claudable
Group=claudable
WorkingDirectory=/srv/claudable/app
Environment=NODE_ENV=production
Environment=HOME=/home/claudable
Environment=PATH=/home/claudable/.npm-global/bin:/usr/local/bin:/usr/bin:/bin
Environment=NEXT_TELEMETRY_DISABLED=1
ExecStart=/usr/bin/npm run start -- --hostname 127.0.0.1 --port 3000
Restart=always
RestartSec=5
TimeoutStopSec=45
KillMode=control-group
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
```

然后执行：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now claudable
sudo systemctl status claudable --no-pager
```

### 4.5 本机验活

```bash
rtk proxy curl -I http://127.0.0.1:3000
rtk proxy curl http://127.0.0.1:3000/api/projects
sudo journalctl -u claudable -f
```

## 5. Nginx 反向代理示例

下面示例只展示主站反代。preview 端口当前不要直接裸暴露到公网。

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

server {
    listen 80;
    server_name claudable.example.com;

    client_max_body_size 50m;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 3600;
        proxy_send_timeout 3600;
        proxy_buffering off;
    }
}
```

启用后按你的常规方式补 TLS 即可，例如 `certbot --nginx`。

## 6. 为什么推荐 `systemd + Nginx`

这个组合和当前仓库实现是顺的：

1. 主站本质上就是一个长期运行的 Node 进程，`systemd` 很适合做守护、重启、日志接管。
2. 仓库本身就假设可以直接访问宿主机 PATH、HOME、SQLite、项目目录和 CLI 登录态。
3. `Nginx` 负责对外域名与 TLS，主站继续只监听 `127.0.0.1:3000`，边界清楚。
4. preview 子进程也跟主站待在同一个宿主机命名空间里，端口、文件路径、CLI 环境都更一致。

## 7. 为什么当前不建议完整 Docker 化

当前代码结构下，完整 Docker 化的主要问题不是构建镜像，而是运行时边界：

1. 你得把所有 CLI 二进制和登录态一起塞进容器，还要保证 `systemd` 服务账号在容器里看到的 `PATH`、`HOME`、认证目录都稳定。
2. 你仍然要给容器挂持久卷，否则 `data/cc.db`、`data/projects/`、`.env.local`、CLI 登录态都会丢。
3. preview 会在平台运行时再拉起每个项目自己的开发服务器，这比普通单 Node 服务更像“宿主机上再孵一批子进程”，不适合先走重容器方案。
4. preview 当前返回的是 `localhost:31xx`，即便主站进了容器，这个地址对外部浏览器仍然不是天然可用的。

所以当前更实际的策略是：

- 主站先用 `systemd + Nginx` 稳定起来
- 数据、CLI、preview 都先按宿主机模型运行
- 如果后面真要容器化，优先单独设计 preview URL 重写和 CLI 登录态管理，再谈整体封装

## 8. preview 远程访问的当前限制

这是当前服务器部署最需要提前讲清楚的点。

当前 preview 链路的行为是：

1. 平台在服务器上为项目分配 `3100-3999` 范围内端口
2. preview 进程通常会把地址写成 `http://localhost:31xx`
3. 前端页面直接把这个 `previewUrl` 塞进 iframe 的 `src`

这意味着：

- 如果 Claudable 主站部署在远程服务器，用户浏览器拿到 `http://localhost:31xx` 后，访问的是“用户自己电脑的 localhost”，不是服务器的 localhost。
- 所以当前主站可以远程访问，但 preview 不能直接按现状对公网用户工作。

当前阶段的可行认知是：

- `systemd + Nginx` 可以稳定承载主站
- preview 更适合服务器本机访问、SSH 隧道访问、VPN 内网访问，或者你自己再做额外的反向代理改造

如果要真正支持公网 preview，至少要补其中一类改造：

1. 让后端返回可公网访问的 preview URL，而不是 `localhost`
2. 由 `Nginx` 按端口或路径统一代理 preview 子项目
3. 前端 iframe 不再直接吃原始 `localhost` 地址，而是走平台域名下的可转发入口

在这部分代码重构完成前，不建议把“远程公网 preview 可用”当作当前部署目标。

## 9. 更新与回滚建议

当前最稳妥的更新顺序：

```bash
cd /srv/claudable/app
git pull
rtk npm ci
rtk npm run prisma:push
rtk npm run build
sudo systemctl restart claudable
```

回滚时优先保证三件事不被覆盖：

- `data/`
- `.env` / `.env.local`
- 运行账号自己的 CLI 登录态

如果这三类东西还在，主站通常能很快恢复。
