# Codex Web 报错分析与解决方案

## 1. 适用范围

本文是本次 Claudable Web 端 Codex/preview 问题的最终版整理。

与前一版相比，这里额外补上了最后一天才确认并修掉的两类问题：

- Codex 在 `turn.completed` 后没有立即把 request 收敛到 `completed`
- Preview 把旧的或未 ready 的 `localhost` URL 长时间暴露给前端

## 2. 最终根因结论

### 2.1 Codex 启动方式原来不稳定

最早的主问题已经确认并修复：

- 原实现直接 `spawn(codex, args)`
- 修复后改成 shell wrapper
- POSIX 用 `sh -lc`
- Windows 用 `powershell.exe`

修复后，Web 后端拉起 Codex 的行为才和终端直跑更接近。

### 2.2 Codex request 的 completed 收敛原来依赖 EOF

这是最后一天补齐的关键修复原理。

原实现的问题是：

- 收到 `turn.completed` 时，只更新内存里的 `hasCompleted` / `terminalOutcome`
- 真正的 `markUserRequestAsCompleted()` 要等流读到 EOF 以后才执行

这会导致一个边缘但很致命的状态：

- Codex 逻辑上已经完成
- 前端可能已经看到最终消息
- 但数据库仍长时间停在 `running`

最终修复原理：

- 在 `turn.completed` 分支里立即执行成功收敛
- 立即 flush assistant 消息
- 立即推送 `completed` status
- 立即调用 `markUserRequestAsCompleted()`
- 不再等待 EOF 作为 request completed 的前置条件

已落地文件：

- `lib/services/cli/codex.ts`
- `lib/services/cli/codex-terminal.ts`
- `tests/codex-terminal.test.ts`

### 2.3 Preview 原来会把失效的 localhost 地址留在前端

“localhost 拒绝连接”这一层，最后确认不是主站 `3000` 没起来，而是 preview 状态同步和 URL 生命周期管理有缺口。

原问题有两层：

1. 项目页初始化时不会主动读取 `/preview/status`
2. iframe 报错时只会重复刷新旧 `src`

所以一旦 preview 端口变更或旧 preview 已失效，页面就会长期访问一个过期的 `localhost:31xx` 地址。

最终修复原理：

- 页面初始化时先同步 `/api/projects/:id/preview/status`
- 如果已有正在运行的 preview，就把真实 `url` 回填给前端
- iframe 报错或用户点击刷新时，不再直接复用旧 `src`
- 先回查 preview 状态，必要时自动重启 preview，再把 iframe 指向新的有效地址

已落地文件：

- `app/[project_id]/chat/page.tsx`

### 2.4 Preview 后端原来会把“没 ready 的地址”也当成功返回

这也是最后一天补的关键修复。

原行为是：

- preview 启动后做 `waitForPreviewReady()`
- 但即使超时未 ready，也会继续返回 `running`
- 同时把 `previewUrl`、`previewPort` 持久化到数据库

这会直接把一个不可用地址发给前端。

最终修复原理：

- Preview 未在规定时间内 ready 时，直接判失败
- 停掉子进程
- 清掉内存态
- 重置数据库中的 `previewUrl`、`previewPort`、`status`
- 不允许前端拿到一条假成功的 `localhost` URL

已落地文件：

- `lib/services/preview.ts`

## 3. 已被修正的旧判断

### 3.1 “多个 request 一直 running”不再是当前最终结论

这个现象在排查早期是真实的，但不是当前代码状态下的最终结果。

最后核查时，那条曾长时间停在 `running` 的 request：

- `project-1779350230695-oozv7vk`

已经收敛为：

- `completed`

因此应更新为：

- 老实现确实可能导致 request 长时间停在 `running`
- 但当前已通过 `turn.completed` 即时 completed 修复掉这条主链路

### 3.2 “localhost 拒绝连接”不等于 preview 根本没启动

最后一天拿到的运行时证据里，先后出现过三种 preview 状态：

1. 旧端口已无效，页面还在访问旧 `localhost`
2. preview 进程起来了，但应用本身返回 `500`
3. preview 重新拉起到新端口后返回 `200`

这说明浏览器里的单一句子不能直接映射为唯一根因，必须结合：

- `/preview/status`
- `/preview/start` 返回体
- preview logs

## 5. 最终修复原理摘要

这次问题到最后真正有价值的修复，不是简单加日志，而是把状态边界修正了：

1. Codex 逻辑完成时就立即 completed，而不是等 EOF
2. Preview 只有真正 ready 时才允许把 URL 暴露给前端
3. 前端不能长期盲信旧的 `localhost` 地址，而要主动回查真实 preview 状态

## 6. 后续排查建议

如果后面再看到类似报错，建议按这个顺序排：

1. 查 `user_requests` 是否真的是 `running`
2. 查 `/api/projects/:id/preview/status`
3. 查 `/api/projects/:id/preview/start` 返回体里的 `logs`
4. 再看上游网络、代理、登录态
