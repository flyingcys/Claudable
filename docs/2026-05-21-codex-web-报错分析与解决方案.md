# Codex Web 报错分析与解决方案

## 1. 问题现象

当前仓库在 `dev` 最新服务启动后，终端里直接执行 `codex` CLI 正常，但在 Web 页面里触发 Codex 时会出现报错、卡住或状态不收敛。

这类现象不能简单归因为“Codex CLI 不可用”。本次排查确认，至少有两层问题叠加：

- Web 后端拉起 Codex 的方式不稳定，导致请求在服务内执行时容易挂住或状态异常。
- 即使本地 Codex CLI 可用，Web 链路里仍然可能遇到上游响应流断开，最终表现为页面报错。

## 2. 根因结论

### 2.1 主根因：Web 侧直接 `spawn(codex, args)` 启动不稳定

`lib/services/cli/codex.ts` 现在已经改成通过 shell wrapper 启动 Codex，而不是直接 `spawn(codex, args)`。

关键实现：

- Shell wrapper 构造：`lib/services/cli/codex-shell.ts:54`
- Codex 启动改为 `buildCodexShellSpawn(...)`：`lib/services/cli/codex.ts:565`
- 实际 `spawn` 的 command/args 来自 wrapper：`lib/services/cli/codex.ts:576`

这次修复前，Web 链路和你手工在终端里执行 CLI 的运行环境并不完全等价。终端里正常，不代表 Node 服务里直接拉起子进程也稳定。修复后通过 shell 包一层，实际行为更接近“人在终端里执行 Codex”，最小真实验证已经可以正常走到 `turn.completed`。

### 2.2 次根因：超时策略过于粗暴，会误杀长任务

之前更像“固定总时长超时”，长任务即使持续有输出，也可能被提前终止。现在改成“10 分钟无活动超时”：

- 无活动超时控制器：`lib/services/cli/codex-shell.ts:99`
- `stdout/stderr` 有活动就续命：`lib/services/cli/codex.ts:583`、`lib/services/cli/codex.ts:631`
- 超时后才杀进程：`lib/services/cli/codex.ts:610`

这解决的是“任务并没死，只是跑得久，但 Web 把它杀了”的情况。

### 2.3 前端状态消费不完整，会把失败态留在等待中

Web 端之前对 realtime status 的消费不够严谨，容易出现后端已经报错或结束，但前端还停在等待态。

当前修复点：

- 改为优先读取后端下发的 `data.status`：`components/chat/ChatLog.tsx:1446`
- 把 `error` 也视为终态，及时清掉等待态：`components/chat/ChatLog.tsx:1406`

这解决的是“后端已经结束，但页面还像没结束一样”的假象。

### 2.4 异步启动失败时，后端之前没有把 request 正确收敛到 failed

`/api/chat/[project_id]/act` 是先返回 `AI execution started`，再异步执行真正的 Codex 任务。这个模式本身没问题，但如果异步启动阶段报错，必须显式把 `user_requests` 标成 failed，并推送 error status。

当前修复点：

- 记录 request 为 `processing`：`app/api/chat/[project_id]/act/route.ts:353`
- 异步失败统一回写 `markUserRequestAsFailed()`：`app/api/chat/[project_id]/act/route.ts:413`
- 同时推送 `status: error`：`app/api/chat/[project_id]/act/route.ts:425`

这解决的是“接口先返回成功，但后台其实已经失败，数据库和页面却没及时感知”的问题。

### 2.5 预览目录 fallback 不一致，会让 AI 修改目录和预览目录分叉

如果项目没有 `repoPath`，`act` 路由和 `preview` 之前落到的目录不完全一致，可能导致：

- AI 实际改了一份目录
- 预览服务却启动了另一份目录

当前已经统一到 `PROJECTS_DIR_ABSOLUTE/<projectId>`：

- `act` 路由解析 project root：`app/api/chat/[project_id]/act/route.ts:379`
- `preview` fallback 目录：`lib/services/preview.ts:624`、`lib/services/preview.ts:705`

这个问题不会直接导致 Codex 启动失败，但会把“Web 上看起来没生效”伪装成 Codex 报错。

## 3. 本次排查拿到的关键证据

### 3.1 Shell wrapper 路径已做真实 CLI 验证

已用 `lib/services/cli/codex-shell.ts` 生成的 wrapper 路径直接跑 `codex exec --json`，能拿到：

- `thread.started`
- `item.completed`
- `turn.completed`

说明新的启动链路本身是通的，不再是旧的 direct spawn 挂死问题。

### 3.2 Web 真实 smoke case 已验证状态链路闭合

在当前修复分支上，使用真实 dev server 做了最小 smoke：

- 运行中：数据库 `user_requests.status = running`
- 同时 `GET /api/chat/<project>/requests/active` 返回 `hasActiveRequests: true`
- 完成后：数据库状态变成 `completed`
- 同时 `requests/active` 返回 `false`

这说明当前分支里，请求状态收敛链路已经正常，`active` 路由和数据库读取没有持续性不一致。

### 3.3 当前仍能复现的报错来自上游响应流断开，不是本地 CLI 不可用

排查中有一条真实 request 最终状态为 `failed`，数据库记录的错误信息是：

```text
Reconnecting... 1/5 (stream disconnected before completion: error sending request for url (https://ocean-code-cn.tuya-inc.com:7799/openai/v1/responses))
```

这条证据很关键，它说明：

- Web 服务已经成功把 Codex 拉起来了
- 失败发生在 Codex 与上游响应服务通信时
- 这不是“本地 codex 命令不存在”或“Web 根本没启动起来”

换句话说，如果你现在看到的是偶发 error，而不是稳定挂死，那剩余风险更偏向网络、代理、登录态或上游服务可用性。

## 4. 为什么会出现“本地 CLI 正常，但 Web 里报错”

原因不是单一的，主要是下面这几个差异：

1. 终端直跑 CLI 和 Node 服务子进程拉起 CLI，不是同一个执行环境。
2. Web 链路还叠加了 request 状态管理、realtime 推送、前端等待态、preview 路径等外围逻辑。
3. Web 链路里即使 Codex 已经成功启动，仍然可能因为上游响应流断开而失败。

所以“本地终端能跑通”只能证明 CLI 基本可用，不能证明 Web 端整条链路已经可用。

## 5. 已落地的解决方案

当前修复分支 `fix/codex-web-exec-hang` 已提交以下修复，提交为 `08c4806 fix: stabilize codex web execution`：

- Codex 启动方式改成 shell wrapper，替代直接 `spawn(codex, args)`
- Windows wrapper 改走 `powershell.exe`，避开 `cmd.exe /c` 的 `%`、`!` 展开风险
- 超时改成“无活动超时”，避免长任务误杀
- 前端 `ChatLog` 正确消费后端 `status`，并把 `error` 当终态
- `act` 路由在异步启动失败时显式落库 failed 并推送 error
- `preview` 的 fallback project 路径与 `act` 路由统一

## 6. 建议处理顺序

### 6.1 先合入当前修复分支

如果线上或你的主开发分支还没有 `08c4806`，先把这批修复带上。否则你会一直混着“本地启动不稳”和“上游偶发失败”两个问题一起看，证据会很乱。

### 6.2 合入后先验证三件事

1. 页面发起 Codex 请求后，`user_requests` 能否稳定从 `processing/running` 收敛到 `completed` 或 `failed`
2. `/api/chat/<project>/requests/active` 是否与数据库一致
3. 页面收到 `error` 后，等待态是否能正确结束

### 6.3 如果仍有报错，再单独盯上游连通性

如果合入本次修复后仍然报错，优先查这几项：

1. Web 服务进程里的 Codex 登录态是否与终端一致
2. Web 服务进程访问 `https://ocean-code-cn.tuya-inc.com:7799/openai/v1/responses` 是否稳定
3. 公司代理、证书、环境变量是否只在交互终端生效，未传到 Web 服务进程
4. 是否存在上游限流、会话过期或短时网络抖动

## 8. 最终判断

这次问题的核心不是“你本地没配好 Codex CLI”，而是 Web 链路原来存在一组实现缺陷，导致：

- Codex 启动方式不稳定
- 长任务可能被误杀
- 失败态没有及时收敛
- 前端容易把失败看成一直在等待
- 预览目录偶尔和 AI 修改目录不一致

这些问题在当前修复分支上已经有明确修复。

如果你合入这批修复后仍然看到 Web 报错，优先把它视为“上游响应流断开/网络或代理问题”，不要再回头怀疑本地 Codex CLI 是否安装成功，因为那一层已经有真实证据表明是通的。
